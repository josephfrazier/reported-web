Semi-Automatic Mode

Upload a folder of photos — or just a pile of loose files — covering many violations at once. The app runs ALPR and reverse-geocoding over the whole batch, groups the photos into violations, and then walks you through them one at a time — form pre-filled, ready to submit.

Grouping algorithm

A new pure module, src/groupAttachmentsByViolation.js, so the whole algorithm is unit-testable without React. In goes one record per processed photo; out comes one record per violation. 

in:  [{ file, name, createDateMs, latitude, longitude,
        plateResults, uploadWidth, uploadHeight }]
out: [{ photos[], plate, licenseState, latitude, longitude, createDateMs }]

The four passes

  1. Sort photos by capture time, so everything downstream can assume chronological order. Missing timestamps fall back to file last-modified and sort last.
  2. Cluster by time and place. Union two photos when Δt ≤ 5000 ms and the haversine distance between them is ≤ 30 m. A photo with no GPS links on time alone. Connected components become candidate violations.
  3. Vote the plate, then split on it. Fold OCR variants together, count how many photos contain each plate, and take the winner. Photos containing it become a violation; the remainder is recursed on. This is what stops two cars photographed back-to-back from merging into one report.
  4. Adopt orphans. Photos with no plate read at all join whichever sub-cluster is nearest in capture time, so a blurry shot still rides along with its violation. Finally, sort the violations earliest-first.

Choosing the plate

Each tie-break is applied only if the one before it is still tied:

  1. Most photos
  2. Most central
  3. ^T\d{6}C$
  4. Highest score

Most central means the smallest mean normalised distance between the plate's box centre and the frame centre, across the photos it appears in. Boxes arrive in the uploaded image's pixel space, and alpr.js already attaches uploadWidth and uploadHeight to the response — normalising against those lets a 4096-wide and a 2048-wide photo be compared fairly. The medallion pattern survives as an extra tie-break, preserving the intent of issue #584.

Why variants must be folded

The checked-in ALPR snapshot reads one medallion four different ways in a single image. Counting exact strings, that is four plates with one photo each — so a two-photo violation would look like two violations sharing no plate, and the vote that picks the plate would have nothing to pick.

t696817c t6968i7c t696b17c t696bi7c

Plate Recognizer hands back its own ranked alternatives in candidates, so folding is a union-find over plate strings whose edges come from candidate-set intersection — no invented edit distance. Note only the clean read matches ^T\d{6}C$, which is exactly why that pattern cannot be the primary signal.

Worked example

Six photos from one walk down a block. Photos 1–3 are the same medallion read three ways; 4–5 are a second car; 6 is a shot where ALPR failed.

# EXIF time Δt From prev. Plate read Violation
108:14:02—— t696817c V1
208:14:064 s3 m t6968i7c V1
308:14:115 s2 m t696817c V1
408:14:2918 s144 m lda8765 V2
508:14:334 s2 m lda8765 V2
608:16:40127 s154 m none V3

Photo 3 → 4 breaks on both signals at once (18 s, 144 m), so V2 opens regardless of plates. Photo 6 → V3 breaks on both as well, and having no plate at all it is flagged rather than discarded. Within V1 the three readings fold into one plate with three photos — the majority it wins is t696817c, the clean read and the only one matching the medallion pattern.

Order of operations matters

Clustering runs before the plate vote, and the plate vote runs before the split. The plate cannot merge two clusters that time and place kept apart — it only ever divides. That keeps the rule one-directional and avoids the obvious circularity of using a plate both to define a group and to be chosen from it.

Caching

The assumption that ALPR results are already cached is half right, and the half that is wrong is the half that matters.

ResultTodayNeeded
ALPR attachmentPlateCache, a WeakMap keyed on the File object (Home.js:225) Nothing new. The queue holds the same File objects, so hits are automatic
Reverse geocode None. setCoords re-queries on every call; the debounce coalesces bursts but stores nothing A small "lat,long" → address memo
Server side Nothing. Both endpoints call through unconditionally Nothing — but see the note on content hashes

Because the ALPR cache keys on object identity rather than content, it only helps while the same File objects are alive. A batch queue holds them for its whole run, which is why no new ALPR caching is required — but a page reload loses everything, matching the decision above.

Geocode once per violation, not per photo

An address is a function of coordinates alone. Forty photos taken at one curb are forty identical lookups today; grouping first means one. This also gives the progress indicator its second stage, which is what the batch was asked to show in the first place.

A ready-made key, if results ever need to persist

Every upload already gets a SHA-256 of its bytes (attachmentId), and identical uploads share a temp file. Nothing consults that hash for results today — the bytes go to Plate Recognizer again even when the hash matches. If reload-survival is ever revisited, that hash is the key to build on.

Module & state

New file

src/groupAttachmentsByViolation.js plus a colocated src/groupAttachmentsByViolation.test.js, following the repo's habit of extracting logic into small pure modules with direct tests.

Two helpers live alongside it:

  • haversineMeters(a, b) — distance between two coordinates
  • normalizedCenterDistance(box, uploadWidth, uploadHeight) — how far a plate sits from the frame centre

Do not reuse handleAttachmentData

It re-runs extraction over the entire attachment array on every add (Home.js:1323). Pointed at a 40-photo folder that re-walks all 40 photos each time a violation is loaded. The batch needs its own one-shot pass.

Two existing functions to get right

  • fetchPlateResults — the batch must use this, because it returns the full response including every results[] entry and is the function the WeakMap already wraps.
  • extractPlate — deliberately not used by the batch. It collapses each photo to a single plate and prefers the medallion pattern, which discards exactly the multi-plate data the grouping needs. The single-violation flow keeps its current behaviour.

Submitting a violation

getPerSubmissionState() already returns precisely the per-submission fields — plate, licenseState, latitude, longitude, coordsAreInNyc, formatted_address, CreateDate, typeofcomplaint, reportDescription, can_be_shared_publicly — and is already wired into the submit payload. Loading a violation sets them through the existing setLicensePlate, setCreateDate and setCoords.

Worth knowing: the name reads backwards. This repo's bundled object.omit (v3) treats its predicate as a keep filter, so despite saying omit the helper returns only those keys.

typeofcomplaint is never auto-filled from a photo — it stays manual, as does reportDescription.

Interface

Ways in

Three inputs feed the same batch, so photos can arrive however they happen to be sitting on disk — in a directory of their own, loose in a camera roll, or dragged straight from a file manager:

  • Add a folder — <input type="file" multiple webkitdirectory>
  • Add photos — a plain <input type="file" multiple>, with no parent directory required
  • Drag and drop — the page is already wrapped in a Dropzone, so dropped files can feed the batch too

All three read event.target.files directly rather than going through the existing FileReaderInput. That component is used with as="buffer", which reads every selected file's contents into memory; across forty photos that is a great deal of buffering before ALPR has even started. (For the record it would accept webkitdirectory — it spreads unknown props onto the real input — it is the buffering that rules it out.)

Picks accumulate, so a folder and then a few stragglers make up one batch. Selection order does not matter: grouping sorts by EXIF time, never by the order files arrived in.

What the toggle changes

With the mode on, every one of these routes feeds the batch. The single-violation flow is what the toggle-off state gives you. Because a folder pick, a loose multi-select and a drop all take the same path, there is never a question of which flow a given pick lands in.

During the batch

An inline <progress> bar on the form, with counts, stepping through ALPR → grouping → geocoding. No modal: the batch is long-running and the user should be able to see the page while it works.

The queue

A list of found violations, each showing its time, plate, photo count and flags. A Load next violation button loads one into the form: its photos appear as thumbnails with the usual plate overlays, and the fields fill from cached results. Submit then advances automatically.

Groups over three photos

The picker shows every photo in the group with checkboxes and the first three selected. It must enforce 3 images and 3 videos, because that is the server's real limit — createSubmission.js takes images.slice(0, 3) and videos.slice(0, 3) and drops the rest without an error. Today the only hint is the button label, and the dropzone enforces nothing at all.

Tests

The algorithm gets direct unit tests; the flow is exercised through the existing Home harness.

  • groupAttachmentsByViolation.test.js — variant folding, plate-driven splitting, both thresholds, and each fallback (no GPS, no time, no plate).
  • Home.test.js — reusing the renderWithFiles harness to assert that violations are found, that loading one fills the fields from cache, that no second /platerecognizer call fires, and that Submit advances.

The best fixture is already checked in. The ALPR snapshot holds exactly the variant case that would break a naive exact-match vote, so a test built on it fails loudly if folding regresses.

Running them

Use yarn test:no-flaky for the full non-network suite. The ALPR, geoclient, srlookup and getVehicleType suites all call live services; run those only deliberately, and always through yarn test, never npx jest — the -r dotenv/config in the yarn script is the only thing loading credentials, so under npx they fail misleadingly.

Risks

  • Plate Recognizer quota POST /platerecognizer carries no rate limit, unlike /api/uploadAttachment (30 per 15 min per IP). A forty-photo folder is forty calls in parallel; the concurrency cap is politeness, not enforcement. Check the plan's quota before running a large batch.
  • Silent 3 + 3 truncation Extras past three images and three videos vanish with no error. The picker has to enforce this or photos disappear between review and submission.
  • Violations outside NYC coordsAreInNyc gates the submit button. Those groups should be flagged in the queue rather than discovered at Submit.
  • Repeated duplicate warnings Reports from one batch resemble each other, so the existing duplicate-submission warning will likely fire over and over as the queue is walked.
  • Videos in scope Supported today (frame-0 grab for ALPR) and assumed included. Say so if they should be excluded from the batch.

Implementation

Three commits, in this order — the algorithm is pure and independently reviewable before any UI touches it.

  1. The module. groupAttachmentsByViolation.js and its tests. Pure, no React, no UI.
  2. The geocode memo. A "lat,long" → address cache, with its own test, so repeated lookups stop re-hitting NYC Planning Labs.
  3. The wiring. Batch state, the three photo inputs, the one-shot processing pass, the queue, load-next, the picker and auto-advance in Home.js, plus the Home.test.js coverage.
